# 基于结构化指令与模拟动作接口的 Agent：现阶段目标与实施计划

## 一、阶段定位

目前已完成“语音输入 → ASR → LLM”的基本流程。本阶段在已有基础上，实现一个能够理解任务、规划执行步骤、调用模拟动作接口，并根据每次执行反馈决定下一步的 Agent。

**本阶段的核心目标是：自然语言指令结构化，以及基于结构化指令的任务规划与循环执行。**

所有动作先在 Python 模拟程序中完成。模拟程序维护位置、执行状态和任务结果，实际验证动作调用是否改变了环境状态。后续提供机器狗后，再根据机器狗 SDK 编写真实动作接口，并进行真机验证。

本阶段暂不接入真实机器人，不要求加入视觉理解、PDDL 规划器、复杂地图导航或机器人底层控制。规划由 LLM 驱动的 Agent 完成，程序负责接口约束、状态管理、结果检查和暂停控制。

## 二、阶段完成后应当具备的能力

系统应支持以下完整流程：

```text
用户文本 / 语音输入
        ↓
ASR 转写（语音输入时）
        ↓
自然语言解析为结构化任务
        ↓
检查任务是否明确、参数是否合法
        ↓
Agent 根据任务和当前状态制定初步计划
        ↓
Thinking：根据任务、历史记录和当前状态决定下一步
        ↓
Action：调用一个动作接口
        ↓
Observation：接收接口结果并更新任务进度
        ↓
检查是否完成 / 是否收到人工暂停
        ↓
未完成且未暂停：进入下一轮 Thinking
```

每次动作调用后，都必须处理执行反馈，再决定下一步。任务正常运行至完成或人工暂停；遇到无法继续的情况，应暂停并说明原因，避免无限循环。

其中，Thinking 在界面和日志中记录简短的决策依据、剩余计划和下一动作即可，不要求模型输出长篇推理文字。

### 典型演示任务

用户输入：

> 先去 A 点检查，再去 B 点检查，最后回到出发点。

预期执行过程：

1. 系统识别任务类型、目标地点、顺序要求和返回要求。
2. Agent 生成初步计划。
3. 调用前往 A 点的接口。
4. 收到到达 A 点的反馈后，决定执行 A 点检查。
5. 收到检查结果后，决定前往 B 点。
6. 完成 B 点检查后，返回本次任务的出发点。
7. 程序核对完成条件，确认任务完成。

用户在任何阶段点击暂停后，系统应停止调度新动作，并保留当前任务和执行进度。

## 三、开发范围与基本约定

### 3.1 支持的任务

先支持两类任务，保证其完整运行：

| 任务类型 | 示例 | 核心要求 |
|---|---|---|
| 前往指定地点 | “去 A 点” | 到达指定地点 |
| 单点或多点检查 | “依次检查 A、B，再回来” | 到达并检查目标地点，按要求返回 |

“检查”在本阶段表示调用模拟检查接口，获得预设或程序生成的结果，不涉及真实摄像头或视觉模型。

任务范围之外的请求应明确提示暂不支持；地点缺失或含义不明确时，只追问影响执行的必要信息。

### 3.2 模拟环境

固定使用三个地点：`home`、`point_a`、`point_b`，分别表示基地、A 点和 B 点。

模拟程序至少维护：

- 当前所在地点；
- 当前运动状态：静止或移动中；
- 当前正在执行的动作；
- 本次任务的出发点；
- 本次任务已完成的检查及检查结果。

地点之间的移动使用短暂延时模拟，不需要实现路径搜索。检查结果可配置为正常或异常，便于重复验证。

### 3.3 模块职责

| 模块 | 负责内容 |
|---|---|
| 指令解析器 | 将自然语言转换为结构化任务 |
| 任务校验器 | 检查字段、任务类型、地点和必要信息 |
| Agent | 根据目标、当前状态和执行历史生成计划并决定下一动作 |
| 动作执行器 | 校验动作参数，调用对应接口 |
| 模拟后端 | 实现动作效果，维护模拟环境真实状态 |
| 任务控制器 | 管理开始、暂停、恢复和完成检查 |
| 日志模块 | 保存每轮决策、动作、反馈和任务进度 |

这些模块可以先写在少量 Python 文件中，不要求搭建复杂框架、微服务或数据库。

## 四、分步骤实施

## 步骤一：定义结构化任务格式

### 做什么

规定自然语言指令需要转换成什么数据，统一模型、Agent 和程序之间的任务表达。

### 应该怎么做

先为两类任务定义固定 JSON 格式。以多点检查任务为例：

```json
{
  "status": "ready",
  "task": {
    "task_type": "inspect_locations",
    "targets": ["point_a", "point_b"],
    "constraints": {
      "visit_in_order": true,
      "return_to_start": true
    },
    "completion_rules": {
      "all_targets_inspected": true,
      "at_start": true
    }
  },
  "clarification_question": null
}
```

格式设计遵循以下规则：

1. `task_type` 使用固定枚举，先支持 `navigate` 和 `inspect_locations`。
2. `targets` 必须使用已知地点标识，不能编造新地点。
3. `constraints` 记录用户明确提出的顺序与返回要求。
4. 完成条件与任务类型及约束保持一致；程序使用固定规则校验或补齐，不能任由模型降低完成标准。
5. “出发点”由程序在任务开始时记录，不能固定理解为基地，也不能在恢复任务时重新覆盖。
6. 输入有歧义时返回 `needs_clarification`，不进入执行阶段。

结构化任务描述的是用户希望完成什么。具体需要调用哪些动作、动作是否重试，由后续 Agent 结合状态决定。

### 结果应该是什么

- 一份任务字段说明；
- 两类任务的合法示例；
- 缺少地点、未知地点和不支持任务的处理示例；
- 一个能检查 JSON 字段和取值的校验函数。

**验收要求：给出一份任务 JSON，程序能判断是否可以进入执行阶段，并指出不合法的字段。**

## 步骤二：实现自然语言到结构化任务的转换

### 做什么

在现有 LLM 调用基础上，增加结构化任务输出与必要的澄清处理。

### 应该怎么做

1. 在提示词中提供支持的任务类型、地点名称、别名和 JSON 格式。
2. 使用模型提供的结构化输出能力；若没有，则解析 JSON 并进行程序校验。
3. 将“ A 点”“A 区”等允许的名称映射为统一标识。
4. 解析失败时允许一次受约束的修正；仍失败则告知用户，不能带着错误参数执行。
5. 对“去检查一下”这类缺少目标的指令，追问检查地点。
6. 保留最小对话上下文，使用户回答“A 点”后能补齐上一轮任务。
7. 先用文本验证，再接入已有 ASR。日志同时保留 ASR 文本和解析结果。

准备约 20 条开发样例，覆盖明确指令、同义表达、顺序要求、返回要求、信息缺失和不支持的任务。

### 结果应该是什么

例如：

| 输入 | 预期结果 |
|---|---|
| 去 A 点 | 前往 `point_a` 的任务 |
| 检查 A 点，完成后回来 | 检查 `point_a`，并返回出发点 |
| 先检查 B 点，再检查 A 点 | 目标顺序为 B、A |
| 去检查一下 | 追问目标地点 |
| 去 C 点 | 提示未知地点或请求澄清 |

**验收要求：输出不仅能解析为 JSON，而且正确保留用户指定的目标、顺序和返回要求。**

## 步骤三：设计动作接口并编写模拟实现

### 做什么

设计少量通用动作接口，让 Agent 可以通过明确参数调用能力，并获得统一反馈。

### 应该怎么做

建议先实现以下接口：

| 接口 | 参数 | 模拟行为 | 成功条件 |
|---|---|---|---|
| `navigate_to` | `target` | 模拟移动并更新位置 | 实际模拟位置到达目标点 |
| `inspect` | `location` | 在当前位置生成检查记录 | 位于指定地点且检查完成 |
| `get_status` | 无 | 返回当前位置和执行状态 | 成功读取状态 |
| `stop` | 无 | 中断或停止当前模拟动作 | 当前动作已停止，系统静止 |

`navigate_to` 和 `inspect` 是主要任务动作；`get_status` 和 `stop` 同时供任务控制器使用。人工暂停必须能够直接触发控制器，不依赖 LLM 决定是否调用 `stop`。

每个接口返回统一结构，例如：

```json
{
  "action_id": "action_003",
  "action": "navigate_to",
  "status": "succeeded",
  "data": {
    "current_location": "point_a",
    "motion_state": "idle"
  },
  "error": null
}
```

动作状态至少区分 `succeeded`、`failed` 和 `cancelled`。检查接口额外返回检查地点、结果和检查记录标识。

模拟实现必须满足：

- 移动完成后才更新“已到达”，不能刚发出请求就算到达；
- 不在目标地点时调用检查，应返回失败；
- 支持设置短暂执行延时，用于验证动作执行中暂停；
- 支持配置“下一次动作失败”，用于后续测试；
- 支持停止后返回明确状态，不能只打印停止提示。

### 结果应该是什么

- 一份动作接口说明；
- 一个模拟后端；
- 可以手动执行“前往 A → 检查 A → 返回”的小程序；
- 成功、失败、取消三类反馈样例。

**验收要求：不接入 LLM，直接调用接口就能验证环境变化、前提检查和停止行为。**

## 步骤四：实现 Agent 的规划与逐步执行循环

### 做什么

让 Agent 根据结构化任务制定初步计划，每次执行一个动作，并在收到 Observation 后重新决定下一步。

### 应该怎么做

**1. 初始化任务上下文。**

保存结构化任务、出发点、当前状态、已完成事项、执行历史和可调用接口说明。

**2. 生成初步计划。**

例如，“依次检查 A、B 并返回”的计划可以是：

```text
前往 A → 检查 A → 前往 B → 检查 B → 返回出发点
```

计划作为后续执行参考，需要允许根据实际反馈调整。

**3. 每轮只输出一个执行决定。**

示例：

```json
{
  "decision_summary": "已到达 A 点，下一步完成该地点检查。",
  "remaining_plan": ["检查 A", "前往 B", "检查 B", "返回出发点"],
  "next_action": {
    "name": "inspect",
    "arguments": {
      "location": "point_a"
    }
  }
}
```

**4. 执行前校验。**

程序检查动作是否在允许列表内、参数是否完整、目标是否合法，以及任务当前是否仍处于运行状态。校验不通过时不调用接口，将错误作为反馈供 Agent 修正。

**5. 执行后形成 Observation。**

Observation 来自真实的模拟接口返回和状态查询，包括成功与否、当前位置、检查记录和失败原因。不能让 LLM 自行编造执行结果。

**6. 更新进度并继续下一轮。**

Agent 根据最新 Observation 判断是继续计划、修正下一步，还是请求暂停。已经完成的检查应有记录，避免重复执行。

**7. 由程序核对完成条件。**

对于多点检查任务，检查所有目标是否具有本次任务的检查记录；要求按顺序时检查记录顺序；要求返回时检查最终位置是否等于本次出发点。

模型可以提出“任务已完成”，但最终完成状态必须通过上述检查。若环境反馈已经满足全部条件，程序也可以直接结束任务。

### 结果应该是什么

- 一个可复用的 Agent 主循环；
- 每轮决策、动作和反馈的清晰日志；
- 可以完成单步和多步任务的演示；
- 一次动作失败后，下一轮决策能够体现失败信息。

**验收要求：每次调用动作后都有对应反馈，下一动作基于最新反馈生成；不能一次生成所有动作后不看结果地连续执行。**

## 步骤五：实现人工暂停与恢复

### 做什么

让用户能够随时暂停任务，系统保留任务进度，并支持后续继续。

### 应该怎么做

设置明确的任务状态：

| 状态 | 含义 |
|---|---|
| `idle` | 尚未开始任务 |
| `running` | 正在决策或执行 |
| `pausing` | 已收到暂停，正在停止当前动作 |
| `paused` | 已停止执行，等待用户处理 |
| `completed` | 完成条件已经满足 |

先提供一个暂停按钮或命令行控制入口。该入口必须在 LLM 请求和模拟动作运行期间仍然可用，可以使用异步任务或独立控制线程实现。

暂停处理流程：

1. 收到暂停请求后立即设置暂停标志，并禁止调度新动作。
2. 若动作正在运行，通过模拟后端的取消机制和 `stop` 接口停止动作。
3. 等待后端确认停止后，将状态改为 `paused`。
4. 保存当前状态、执行记录和剩余任务。
5. 如果 LLM 的上一轮结果在暂停后才返回，不能据此启动新动作。

用户恢复时，先读取最新状态，再进入下一轮决策。恢复过程中继续使用原任务出发点和已完成记录。

### 结果应该是什么

至少验证以下情况：

- 模型生成决策时暂停；
- 模拟移动过程中暂停；
- 两个动作之间暂停；
- 暂停后继续执行。

**验收要求：暂停后不再启动新动作，界面区分“正在暂停”和“已经暂停”；恢复后不无故重做已完成任务。**

## 步骤六：加入最基本的异常处理

### 做什么

处理少量常见错误，确保 Agent 能报告问题并受控停止。

### 应该怎么做

第一版只处理以下情况：

| 情况 | 处理方式 |
|---|---|
| LLM 输出格式错误或未知动作 | 返回校验错误，允许有限次修正 |
| 动作临时失败 | 将错误传入下一轮，允许有限重试 |
| 连续执行失败 | 暂停并说明失败原因 |
| 模型请求或动作超时 | 停止调度，必要时停止当前动作，暂停并报告 |
| 多轮执行没有任务进展 | 达到轮数或重复动作上限后暂停 |

重试次数和最大执行轮数使用可配置参数，例如单个动作最多重试两次、单任务最多二十轮。具体值通过开发案例调整。

如果某次调用超时，不能默认动作一定没有发生。应先查询状态，再决定是否重试，避免重复执行。

本阶段不要求复杂故障诊断或自主修复。发生超出当前能力的问题时，保留日志、暂停并等待用户处理即可。

### 结果应该是什么

- 一个可以主动注入单次失败的模拟场景；
- 一个连续失败后暂停的场景；
- 无任务进展时能够终止循环；
- 日志中明确记录暂停原因。

**验收要求：错误不会被当作成功，系统不会在重复失败的情况下无限调用接口。**

## 步骤七：完成模拟验证与演示

### 做什么

用一组固定案例验证本阶段目标，整理可交付的代码与说明。

### 应该怎么做

先完成以下验收案例：

| 编号 | 场景 | 预期结果 |
|---|---|---|
| 1 | 去 A 点 | 到达 A 点并完成任务 |
| 2 | 检查 A 点 | 到达 A 点，产生检查记录 |
| 3 | 依次检查 A、B | 检查顺序正确 |
| 4 | 检查 A、B 后返回 | 检查完成且回到任务出发点 |
| 5 | 从 B 点开始任务，检查 A 后回来 | 最后返回 B 点 |
| 6 | “去检查一下” | 请求补充目标，不直接执行 |
| 7 | 输入未知地点 | 请求澄清或提示不支持 |
| 8 | 第一次移动失败 | 下一轮使用失败反馈，按规则重试或暂停 |
| 9 | 连续动作失败 | 达到上限后暂停并报告 |
| 10 | 移动中人工暂停 | 动作停止，后续动作不启动 |
| 11 | 等待模型响应时暂停 | 迟到的模型输出不触发动作 |
| 12 | 暂停后恢复 | 基于最新状态继续剩余任务 |

任务结构化可以使用开发样例之外的新表述再做一次检查，避免只记住固定说法。正式验收至少保留一次完整运行日志；包含随机性的案例重复运行并记录成功次数。

日志至少包含：

- 任务编号、原始文本及结构化任务；
- 每轮序号和简短决策说明；
- 动作名称、参数、开始时间和结束时间；
- Observation 与当前任务进度；
- 暂停、恢复及最终完成检查结果。

开发期间优先使用文本控制台或简单界面，不把时间投入复杂展示页面。

### 结果应该是什么

- 一套可运行的模拟演示程序；
- 验收案例及实际运行结果；
- 正常执行、人工暂停和失败处理的演示记录；
- 安装、配置和启动说明；
- 已知限制及下一阶段待办事项。

**验收要求：能够从一条新任务开始，完整展示结构化解析、初步计划、逐轮执行反馈、人工控制和最终结果检查。**



## 五、与后续机器狗阶段的衔接

本阶段设计接口时，应将 Agent 与具体执行后端分开：

```text
结构化任务 → Agent → 统一动作接口 → 模拟后端
                               └→ 后续机器狗后端
```

后续接入机器狗时，主要新增以下内容：

1. 根据机器狗 SDK 实现移动、状态读取和停止等动作。
2. 根据实际传感器和任务要求实现检查能力。
3. 将接口返回值转换为本阶段已经使用的统一 Observation 格式。
4. 根据真机能力调整可调用动作列表、超时参数和任务限制。
5. 从单动作验证开始，再逐步验证多动作任务和人工暂停。

需要注意，模拟中的 `navigate_to(point_a)` 表示离散地点移动。真机是否能够实现“前往 A 点”，取决于是否具有定位、地图和导航能力。如果 SDK 只提供速度控制，则需要额外开发导航适配层，或先将任务限定为定时移动、转向等可可靠执行的动作。

因此，本阶段应保证接口含义和反馈格式清楚，为后续适配提供基础；不能把模拟接口通过等同于真机已经具备相应能力。人工暂停在真机上也必须经过实际停止与状态反馈验证。

### 阶段完成标准

**给系统一条支持范围内的自然语言任务，它能够转换为合法结构化指令，由 Agent 规划并逐次调用模拟动作接口；每次调用后读取 Observation，再决定下一步；最终通过状态检查确认任务完成，或响应人工暂停并保留进度。**

本阶段以这条完整、可检查、可暂停的模拟执行链路作为主要成果。
